## 1. 十一个会静默失败的坑（最贵的一类）

这些坑的共同点：**不报错、退出码 0、看起来成功**。

### 1.1 磁盘写满，渲染器仍返回 0

`tools/render.mjs` 统计的是「尝试写的帧数」，不是「成功落盘的帧数」。
磁盘满时它逐帧打印 `ENOSPC`，最后仍报 `0 failed` 并 `exit 0`。

- **实际后果**：一次运行产出 1359 个 0 字节帧，报告"成功"
- **防御**：`npm run check:frames` —— 查帧数、0 字节、索引断层、PNG 头
- **更好**：用 `render-segmented.mjs`，它每段编码前强制核验

### 1.2 `-shortest` 截断音轨

用 `-shortest` 混音，配合 **concat 拼接出来的视频**输入，会把音频截短。

- **实际后果**：容器头声明 161.02 秒，实际只装了 134.36 秒 —— 少一整段，
  四个新格完全没声音，而文件大小和退出码都正常
- **防御**：显式 `-map 0:v:0 -map 1:a:0`，**不要 `-shortest`**；
  混音后立刻 `ffprobe` 比对音轨时长
- **验证**：`npm run check:sync`

### 1.3 段文件名用递增序号 → 静默覆盖

`seg_000/seg_001/...` 这种命名，第二次从中间帧开始时又会把第一块叫 `seg_000`，
**覆盖**已完成的段。

- **实际后果**：丢了 2410 帧（约 6 分钟渲染）
- **修法**：段文件名用**首帧号**（`seg_02410.mp4`），不可能撞

### 1.4 ffmpeg 找不到非 0 起点的帧序列

`-i frames/f%05d.png` 默认从索引 0 找。一段从 `f02410.png` 开始时，
报 `could find no file or sequence`。

- **修法**：`-start_number 2410`

### 1.5 `drawPen` 的 `color: false` 把填充强制为白色

`src/rig/pen.js` 里，`color: false` 会让每个填充部件变成 `#ffffff`，
**盖掉底层已经画好的颜色**。

- **实际后果**：连着五次尝试让鹈鹕变金色都失败，鸟身始终是白的
- **根因定位过程**（值得记住的方法）：
  1. 在渲染出的画布上**采样鸟身像素** → 返回背景色，证明颜色根本没画上去
  2. 画一个**洋红测试矩形** → 出现，证明 p5 填充在场景里工作正常
  3. 于是排除填充机制，锁定到 `drawPen` 的白色强制填充
- **修法**：`strokeOnly: true`（只描边不填充），剪影自己画

### 1.6 网格容量与场景数脱钩 → 三格静默不画

片尾展墙原本是 `COLS = 7, ROWS = 3` = 21 格，但加上 4 个新场景后
`N_CELLS = N_SCENES + 1 = 25`。`panelCentre()` 里

```js
const r = Math.floor(i / COLS);   // 最后四格算出 r = 3
const k = T_ROW[r];               // T_ROW 只有 3 项 → undefined
```

`k` 变 `undefined`，位置算出 `NaN`，**拜占庭、面具、包豪斯三格完全没有画出来**，
席位则掉到墙外一行。整条链路不报任何错。

- **为什么难发现**：这属于"少画了东西"，不是"画错了东西"。
  画面看起来完整、构图也说得过去，只是少了三格。
- **抓到的办法**：把片子看到结尾，**数格子**。19 格、21 格、24 格肉眼可分辨。
- **修法**：`COLS = 8`（24 = 8×3 正好满墙）；锚点改为按末格列号推算而不是写死
  `- 2 * GP`（那只对 7 列成立）；`wallC()` 给席位单独返回坐标。
- **更重要的教训**：网格尺寸应该**由元素数量推导**，不要两个地方各写一个数。

### 1.7 CI 里写死片长，把发布流水线锁死

`.github/workflows/publish.yml` 的校验步骤写了 `if (FRAMES !== 8220) process.exit(1)`。
片子扩到 9660 帧之后，**每一次打 tag 都在十秒内失败**，npm 包因此一直停在 2.0.0。

- **为什么三周没发现**：Release 页面一切正常（成片、配乐都在），
  只有点进 Actions 或看邮件才知道。**产物正常 ≠ 流水线正常。**
- **修法**：改成自洽校验 `FRAMES === round(DURATION × FPS)`，
  并检查 `N_SCENES` 为正整数。断言该拦的是"坏掉的树"，
  不该把"编辑"冻住 —— 任何写死片长的检查都活不过下一次加格。

### 1.8 发布步骤不幂等 → 修好之后仍然红

移动 tag 之后重跑，报 `E409 Cannot publish over existing version`。
版本已经发布过，但流水线把它当成失败。

- **修法**：先 `npm view "$NAME@$VER" version`，已存在就打 `::notice::` 并 `exit 0`
- **教训**：凡是"有副作用的外部操作"，先查状态再动手，天然可重跑。

### 1.9 `-c copy` 拼接会带时间戳漂移，别修补脏交付物

试过只重渲尾声再拼回旧片，失败两次：

1. 从旧成片 `-c copy` 抽出前段后，时间戳本身已经不单调 ——
   8939–8942 帧处实测 `148.971 → 149.021 → 149.004 → 149.088 s`
2. 拼回去总长变成 **161.055 s**，而不是 161.021 s

**不要修补一个时间戳已经不干净的交付物，要重建它。**

### 1.10 「它是最后一格」这个假设藏在三个地方，加格全崩

在末尾追加四格之后，`npm run check` 一次报出三个错误，根因是同一个：
代码里三处假设 *`code` 是最后一格*。

| 假设藏在哪 | 后果 |
|---|---|
| `20-code.js` 的 `ride.stopAt = 500` | 骑手停两次：先在 code，再到真正的最后一格 |
| 接缝检查写成「最后一格 **或** 入口接缝才放过偏移」 | code 的 `path()` 偏移靠身份蒙过去；它变成中间格后检查反而失败，而画面是对的 |
| 四格的 `hold` 长度 1.6–2.7 s（原版 0.9–1.7 s） | 行程损失 2.08 s（上限 1.0）、接缝加速度 38/−24（允许 ±30） |

- **修法**：`stopAt` 由 `index.js` 统一补给"真正的最后一格"；
  接缝偏移改为场景显式声明 `seamOffsets: true`；`hold` 收紧到 1.1–1.4 s。
- **教训**：代码里出现「第一个 / 最后一个 / 中间那个」这类身份判断，
  就是一个待爆的硬编码。**改成由数据声明** ——
  用 `N_SCENES - 1` 而不是 scene id，用 `seamOffsets: true` 而不是 `i === 20`。

### 1.11 检查器里的例外要写成"可声明"，不能靠猜身份

`app.js` 原来的条件 `i < N - 1` 意思是"只有最后一格允许偏移"。
这在 20 格时正确，在 24 格时就变成**对正确画面的误报**。

例外本身没问题（有些格确实需要特殊构图），错在**例外是靠位置推断的**：
那个元素一挪位置，例外要么错误放行、要么错误拦截。
改成显式声明后，检查器不再需要猜。

## 2. 验证方法（这里的方法救了三次）

### 2.1 不要相信退出码，要量实际产物

| 想知道 | 别做 | 要做 |
|---|---|---|
| 帧是否都在 | 看 `0 failed` | 数文件 + 查 0 字节 + 查索引断层 |
| 音频是否完整 | 看容器头 `duration` | **解码成 PCM，数字节** |
| 画面是否正确 | 看渲染成功 | 抽帧拼图，**用眼睛看** |
| 元素是否都在 | 觉得画面"看着完整" | **数格子**：该 24 格就是 24 格 |
| 发布是否成功 | 看 Release 页面 | 看 **Actions 运行结果** + 查 npm 上的版本号 |
| 响度是否达标 | 看 peak | `ffmpeg -af ebur128` 看 LUFS |

容器头的 `duration` 会骗人。`ffprobe` 报 161 秒而实际只有 134 秒那次，
就是解码后数字节才发现的。

### 2.2 音频检测要在目标点测量，不要全局找

找「切格点上的车铃」时，前两版都错了：

1. **全局 top-0.1% 阈值** → 只找到 7/24 个铃
2. **局部峰值检测** → 19/24

原因：安静段落里的铃是全局大事件，响亮段落里的同一只铃不是。
实测那 24 个点的能量峰都落在拍点 **±0.004–0.010 秒**内，**从来就没错**，
只是被音乐盖住了。
**最终方案**：在切格点处直接问「有没有局部能量跃升」，不做全局检测 → 24/24。

> 教训：检测器说"没有"，不等于"不存在"。先怀疑检测器。

### 2.3 预览图取帧要等相机就位

从成片抽帧做 README 预览图时，取每格 `+3.2s` 会拍到相机还在推面板的过程，
每格都带着相邻面板的边缘，看起来像三联画。

- **修法**：取 `+4.7s`（相机已就位），并裁掉外侧 40%
- 文件名：`tools/preview-strip.mjs`

## 3. 这个项目的架构要点

### 3.1 三层画布（必须记住）

| 层 | 内容 | 为什么 |
|---|---|---|
| 2D 底层 | 文字、标题、字幕 | **p5.brush 会清掉 p5 的 `text()`** |
| WEBGL | 所有笔刷美术 | p5.brush 必须在 WEBGL 上工作 |
| 合成 | 拍平成一张 PNG | 交付给编码器的是单一帧 |

### 3.2 `env.fit()` 只能由场景调用一次

调度器再包一层就是双重变换，画面缩到左上角 40%。

### 3.3 共享骨架，24 种画法

所有时代共用 `src/rig/pelican.js` 的同一副骨架，每个场景只负责用自己的技法画它。
这是鹈鹕跨画框能严丝合缝的原因。

### 3.4 烘焙

重场景（宋代山水约 200 笔皴法）超出每帧预算十倍。
实测 p5.brush：20–60 笔 3–12ms，240 笔 55–120ms，400 笔 140–225ms。
静态层只烘焙一次，之后每帧只画动的部分。

## 4. 性能与环境（本机实测）

| 项目 | 数值 |
|---|---|
| 单帧渲染（RTX 4060 / D3D11） | 稳态 7–8 fps，轻格 14 fps |
| 全片 9660 帧 | 约 55 分钟（6 worker） |
| 单帧 PNG 均值 | 3.1 MB |
| 全片 PNG | 约 29 GB |
| 分段渲染峰值磁盘 | 单段 1600 帧 ≈ 5 GB |
| 配乐离线渲染 | 161 秒配乐约 520–565 秒 |
| 成片 | 333 MB / H.264 + AAC |

### Windows 适配（原版只支持 macOS）

`tools/lib/browser.mjs` 三处改动：

| 原本 | Windows |
|---|---|
| Chrome 路径写死 macOS | 按平台探测，`CHROME_PATH` 优先 |
| `--use-angle=metal` | `--use-angle=d3d11 --force_high_performance_gpu` |
| `protocolTimeout` 180s | 设为 0（配乐渲染要跑数分钟） |

`PT_SOFTWARE_GL=1` 可退回 SwiftShader。注意：只给 `--use-gl=swiftshader`
不够，必须 `--use-angle=swiftshader --enable-unsafe-swiftshader`，
否则 p5.brush 报 `compiling the vertex shader: null`。

## 5. 网络限制（本机）

| 目标 | 状态 |
|---|---|
| `github.com`、`raw.githubusercontent.com` | **被阻断**（000 / Connection reset） |
| `api.github.com` | 可用 |
| `git push` | **失败**（RPC failed, curl 56） |

**所以推送必须走 API**：`npm run publish:api`（`tools/push-via-api.mjs`），
它用 Git Data API 逐文件上传 blob → tree → commit → 更新 ref。
提交历史是真实的，不是打包上传。

> 已验证：用这种方式推送的仓库，远端文件与本地逐字节一致（md5 相同）。

**开代理之后仍然如此**（用户后来开了代理）：

- 代理只对 `api.github.com` 生效，`git ls-remote origin` 依旧
  `Recv failure: Connection was reset`，`curl https://github.com` 返回空
- 环境里没有任何 proxy 变量，所以 `gh` 和该脚本能用，git 协议不能用

**两个 API 推送特有的副作用**：

1. **commit sha 会被重写**。脚本新建的 commit 与本地 HEAD 的 sha 不同，
   但 tree 内容一致。所以本地 tag 和远端 tag 的 sha 对不上是正常的 ——
   对齐要看**内容**，不要看 sha。
2. **推送偶发失败不会自动重试**。第一次推 `docs(changelog)` 时报错退出，
   原样重跑就成功了。**不要因为一次失败就改代码**，先重跑一次。

## 7. 工作流（做完一次要跑这些）

```bash
npm run audio              # 1. 合成配乐
npm run render:segmented   # 2. 分段渲染+编码+拼接
npm run check:frames       # 3. 帧序列完整性
npm run check:sync         # 4. 音画同步（24 个切格点）
npm run preview            # 5. 重新生成 README 预览图
npm run publish:api        # 6. 推送到 GitHub（git push 被墙）
```

**出片前一定要跑 check:frames 和 check:sync。** 这两个脚本正是因为踩过坑才写的。

### 7.1 分段渲染的两个开关（中断后必用）

```bash
node tools/render-segmented.mjs --seg 1600 --skip-existing --workers 6
```

- 每段内部**永远传 `--resume`**：段渲完即删帧，正常流程零成本；
  中断后重跑只补缺的帧
- `--skip-existing`：段文件存在且非空就跳过该段，**但仍计入最后的拼接**

> **陷阱**：不加 `--skip-existing` 而用 `--from 6400` 续渲，
> 最后只会拼出尾段 —— 静默产出一支两分钟的片子。
> 段列表必须是"全片"而不是"本次渲染的部分"。

### 7.2 发布与 CI

```bash
gh workflow run publish --repo mengxing123456789/pelican-test --ref main
gh run list --repo mengxing123456789/pelican-test --limit 3
```

**`gh release` 在后台 job 里会失效**，原因有两个，都得绕：

- 后台 job **不继承 workdir** → 相对路径报 `no matches found`
- 后台 job 里 gh **没有仓库上下文** → 报 `release not found`

所以：**绝对路径 + 显式 `--repo mengxing123456789/pelican-test`**。

## 8. 文档规范（本项目的约定）

每轮改动后要同步更新：

| 文件 | 写什么 |
|---|---|
| `README.md` | 架构、实测数据、参考来源、当前状态 |
| `CHANGELOG.md` | 按版本号记录：改了什么、**为什么**、验证了什么、**根因是什么** |
| `docs/PROVENANCE.md` | 版本关系与证据（面向公开读者，不要写本地路径） |
| `docs/MEMORY.md` | 本文件：踩过的坑、验证方法、教训 |

CHANGELOG 里值得写的不只是"改了什么"，而是**"排除过哪些可能"**。
上面第 1.5 节那次，五次尝试中前四次的方向都是错的，那才是下次能省时间的地方。

**根目录要保持只有 4 个文件**：`README.md`、`CHANGELOG.md`、`LICENSE`、
`THIRD_PARTY_NOTICES.md`。其余一律进 `docs/`，否则访客第一眼看到的是杂物。

## 9. 如果重新开始，我会怎么做

1. **先量产物再报成功**。任何"完成"都要有对应的实际检查，不看退出码。
2. **磁盘先算清楚**。全片 PNG 29 GB，逐段渲染而不是整批。
3. **段文件用帧号命名**。
4. **视频和音频分开验证**：容器头不可信，解码数样本。
5. **画布颜色不对时，先采样像素**，别猜。
6. **推送用 API**，每次推完回读远端内容确认。
7. **CHANGELOG 记根因和排除过程**，不只是结论。
8. **任何数量都从源头推导**：片长、网格尺寸、字幕里的"第几个时代"，
   一律从 `N_SCENES` / `DURATION` 算，不要在第二个地方写死一份。
   这一个错误在这项目里犯了三次（字幕说 20 个、展墙画 21 格、CI 断言 8220 帧）。
9. **断言要自洽，不要冻结编辑**。检查"树是否自相矛盾"，而不是"是否还是上个版本"。
10. **有副作用的操作要幂等**：发布前先查是否已经发过，
    推 tag 前先想清楚会不会重复触发。
11. **看那些不在产物里的信号**：CI 结果、npm 版本号、邮件。
    这次正是"Release 页面完全正常、npm 停在两个月前"。
12. **数元素**。该有 24 格就数到 24，别用"看起来挺完整"过关。

## 10. 附录：v2.2.2 这一轮到底发生了什么

留给下次的现场记录。顺序就是实际发生的顺序。

### 起因
用户发现邮箱里一堆 GitHub Actions 失败通知：
「不对啊，你这些提交都是怎么回事，我邮箱为什么显示报错了」。

### 三个独立的问题（不是一个）

### 如果再遇到「CI 一直红」
按这个顺序查，别先怀疑代码：
1. `gh run list --repo <repo> --limit 5` 看是哪几次、多久失败
2. **十秒内失败**通常是校验步骤（断言/依赖安装），不是编译或测试
3. `gh run view <id> --log-failed | grep -E "npm error|Error|unexpected"` 直接看错误行
4. 判断这条流水线是「产物坏了」还是「检查坏了」——
   这次是检查坏了，产物一直是好的
